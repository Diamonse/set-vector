# SetVector desktop integration

**Recommendation: build the first installed Windows and macOS application with PySide6, native library and job controls, and an embedded Qt WebEngine chart view.** This is an engineering judgment based on SetVector's Python core and existing HTML reports; no candidate desktop build was benchmarked during this research. Package the analyzer as a separate executable so analysis remains responsive, cancellable at the process boundary, and independent of the interface. The application can import local music, analyze it, display results, and preview audio without DJ software, installed Python, GPT access, or a running cloud service. Direct signed distribution is the assumed route: Qt WebEngine is incompatible with the Mac App Store. Choose Tauri instead if a predominantly web interface or store strategy changes the product requirements, while preserving the same Python worker contract. ([Qt for Python](https://doc.qt.io/qtforpython-6/), [Qt WebEngine platform notes](https://doc.qt.io/qt-6/qtwebengine-platform-notes.html), [Tauri sidecars](https://v2.tauri.app/develop/sidecar/))

## PySide6 provides the closest fit to the existing application

Qt exposes desktop controls directly to Python, and `QWebEngineView` can display the existing interactive HTML report inside an application window. **Inference:** use native file selection, menus, library rows, queue controls, settings, and errors around the chart. This provides a complete desktop workflow while limiting new language and runtime boundaries. It still requires deploying Chromium resources and helper executables; it is not a minimal-runtime solution. ([Qt for Python](https://doc.qt.io/qtforpython-6/), [QWebEngineView](https://doc.qt.io/qt-6/qwebengineview.html), [WebEngine deployment constraints](https://doc.qt.io/qt-6/qtwebengine-platform-notes.html))

Tauri is the strongest alternative for a web-led product: it supports packaged Python sidecars, bidirectional process communication, scoped native permissions, installers, and updates. Its Windows WebView2 and macOS WKWebView require separate rendering and playback validation. Electron supplies a consistent bundled Chromium environment but adds Chromium/Node and a separately packaged Python engine; pywebview offers a smaller Python-to-web integration surface but leaves more distribution decisions to the application. **Inference:** prefer Tauri when custom web UI dominates, Electron when measured browser compatibility justifies its runtime, and pywebview for a limited prototype. No source establishes which complete SetVector bundle would be smallest or fastest. ([Tauri sidecars](https://v2.tauri.app/develop/sidecar/), [Tauri webviews](https://v2.tauri.app/reference/webview-versions/), [Electron security and runtime responsibilities](https://www.electronjs.org/docs/latest/tutorial/security), [pywebview architecture](https://pywebview.flowrl.com/guide/architecture.html))

## The catalog and worker can reuse the current Python core

The audited implementation already exposes `analyze_track(path, config, store)` with cached artifact reuse and `render_report(feature_id, store, ...)` without reanalysis. Reports can use a relocated audio path or omit audio when the original is missing. The CLI emits structured JSON results, but its operations are synchronous: granular progress, a persistent job protocol, and cooperative cancellation are future work. Artifact identities include content and extractor/configuration/dependency identity; stronger source-revision provenance described in the architecture is not fully implemented. These observations describe the research audit at revision `96e60400bde4f83ec15719fce81fd3cba8fd6c60` and should be checked against subsequent analysis changes. ([Analysis service](../src/setvector/application/analyze.py), [Report service](../src/setvector/application/report.py), [CLI](../src/setvector/cli/__init__.py), [Identity implementation](../src/setvector/analysis/identity.py), [Architecture](../docs/architecture.md))

**Proposed integration:** desktop window → application coordinator and local catalog → packaged analyzer process → existing application services and immutable artifacts. Give the desktop adapter ownership of UI state, import, jobs, and locations; preserve numerical and feature-schema ownership in the existing core. Start one process per analyzed track using argument arrays and the current JSON command output. Introduce a versioned newline-delimited JSON protocol when richer control is needed, carrying request/job IDs, stages, terminal status, small summaries, and artifact references. Keep logs on stderr and large arrays in artifacts. A startup handshake should expose engine/protocol versions and capabilities. These are design recommendations, supported by the existing CLI boundary and documented sidecar mechanisms. ([CLI](../src/setvector/cli/__init__.py), [Architecture](../docs/architecture.md), [Tauri sidecar communication](https://v2.tauri.app/develop/sidecar/))

**Proposed catalog:** SQLite records library entries, file locations, content identities, analysis references, jobs, and later annotations/playlists. Keep `feature_id` as the durable result link. A path is a location, and multiple locations can contain identical bytes; retagging currently changes whole-file identity. Import should display discovered files progressively before completing every content hash. Keep one catalog writer in the coordinator, with workers publishing artifacts and returning references. Store the active database in local application data outside network or sync folders, use migrations and database-aware backups, and distinguish durable analyses from disposable previews. SQLite WAL permits concurrent reading but only one writer and requires same-host access; platformdirs supplies suitable application directories. ([Audio inspection](../src/setvector/ingestion/audio.py), [Artifact store](../src/setvector/storage/artifacts.py), [SQLite WAL](https://sqlite.org/wal.html), [Platformdirs](https://platformdirs.readthedocs.io/en/latest/tutorial.html))

Persist queued, running, completed, failed, cancelled, and interrupted jobs. **Inference:** expose track counts and elapsed time initially; add stage callbacks before promising precise percentages. Hard cancellation should terminate only the dedicated worker. On restart, reconcile validated published artifacts with unfinished jobs, because publication and catalog completion are separate operations; remove abandoned temporary directories only after excluding live writers. Avoid killable shared multiprocessing queues, which Python documents as vulnerable to corruption on termination. Begin with explicit rescan and relink; filesystem watchers can later signal a rescan but do not reliably preserve identity through every rename. ([Artifact publication](../src/setvector/storage/artifacts.py), [Python multiprocessing](https://docs.python.org/3/library/multiprocessing.html), [Qt filesystem watcher](https://doc.qt.io/qt-6/qfilesystemwatcher.html))

## Report reuse should lead to lightweight charts and one playback clock

The current report embeds chart assets, feature arrays, and base64 audio, then synchronizes its chart to an HTML audio player. **Proposed first slice:** load the generated local HTML report and validate playback in the packaged application. Use file navigation rather than `setHtml()`, whose documented data-URL limit is approximately 2 MB. **Proposed production design:** retain self-contained HTML as export, load reusable in-app chart assets and feature data on selection, and keep audio in its original file or a separate preview cache. This avoids repeated large HTML assembly. ([HTML report](../src/setvector/visualization/html.py), [Report player](../src/setvector/visualization/assets/report.js), [Preview generation](../src/setvector/ingestion/preview.py), [QWebEngineView](https://doc.qt.io/qt-6/qwebengineview.html))

For integrated Qt playback, `QMediaPlayer` provides transport, seeking, position, and error signals, while WebChannel can exchange seek requests and time updates with the chart. **Inference:** define a playback adapter with play, pause, seek, position, duration, and error operations; use the player as the single authoritative clock. Convert milliseconds to SetVector source seconds at that boundary, and validate preview offsets and compressed-file seeking. Qt Multimedia and Qt WebEngine use different media paths, so successful Python decoding does not establish browser or native playback compatibility. Qt explicitly recommends testing media behavior on target platforms. ([QMediaPlayer](https://doc.qt.io/qt-6/qmediaplayer.html), [WebChannel](https://doc.qt.io/qt-6/qtwebchannel-javascript.html), [Qt Multimedia](https://doc.qt.io/qt-6/qtmultimedia-index.html), [WebEngine codecs](https://doc.qt.io/qt-6/qtwebengine-features.html))

**Proposed initial format matrix:** test WAV, AIFF, FLAC, and MP3 independently for analysis and playback. Do not promise AAC/M4A decoding from the current libsndfile path. Metadata-readable, analyzable, and playable are separate capabilities. The current overview derives from analysis features, and downbeat output is empty; a precise PCM waveform and validated downbeat analysis would be additional work. Multiresolution min/max envelopes can become separately versioned display artifacts. Imported tags, analyzer estimates, and user corrections should retain separate provenance; Mutagen supports broad metadata reading but uses GPLv2-or-later licensing, so dependency selection requires a distribution decision. ([libsndfile formats](https://libsndfile.github.io/libsndfile/formats.html), [Report model](../src/setvector/visualization/model.py), [SoundFile block reading](https://python-soundfile.readthedocs.io/en/latest/), [Mutagen](https://mutagen.readthedocs.io/en/latest/))

## Packaging and installed tests determine release readiness

**Proposed packaging spike:** build a pinned PyInstaller directory bundle containing the UI, Python worker, numerical libraries, decoders, and Qt resources; evaluate `pyside6-deploy` if it handles this dependency set better. PyInstaller builds are platform-specific, while `pyside6-deploy` wraps Nuitka and produces application bundles rather than a complete installer/update policy. Build Windows x64 and macOS arm64 on their corresponding systems; add a separate Intel Mac build only if selected for release. A universal macOS bundle requires compatible architecture slices throughout its dependencies. ([PyInstaller operation](https://pyinstaller.org/en/stable/operating-mode.html), [PyInstaller macOS architectures](https://pyinstaller.org/en/stable/feature-notes.html), [pyside6-deploy](https://doc.qt.io/qtforpython-6/deployment/deployment-pyside6-deploy.html))

Distribute complete signed installers, with Developer ID signing and notarization for direct macOS delivery. Windows signing identifies the publisher but does not guarantee freedom from SmartScreen warnings. **Inference:** begin with manual replacement installs and user data outside the installation directory; add optional signed updates after recovery and migration behavior is proven. Network access must never gate analysis startup. Tauri's offline Windows deployment can include WebView2, illustrating why a small shell does not establish a small complete offline installer. ([macOS distribution signing](https://v2.tauri.app/distribute/sign/macos/), [Microsoft SmartScreen](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation), [Tauri Windows installers](https://v2.tauri.app/distribute/windows-installer/))

**Release gates proposed by this research:** install on clean machines without Python or developer tools, block networking, then import, analyze, reopen cached results, preview, seek, export, interrupt, restart, and upgrade. Test each promised codec, long tracks, malformed media, missing or moved files, removable disks, Unicode and long paths, and read-only music folders. Validate keyboard operation and screen-reader alternatives to canvas-only charts. Test worker death during decoding, extraction, and publication, and confirm UI/playback remain responsive under load. These tests have not been executed. Framework accessibility and deployment support provide mechanisms, not application-level proof. ([PyInstaller operation](https://pyinstaller.org/en/stable/operating-mode.html), [Qt accessibility](https://doc.qt.io/qt-6/accessible.html), [Windows paths](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation))

Treat filenames, tags, and reports as untrusted input: escape metadata, restrict web navigation/resource access, and expose narrow bridge operations. A local HTTP service would additionally need session authentication and origin/host validation; it is unnecessary for the proposed process protocol. Before distribution, inventory numerical, Qt, FFmpeg, metadata, and codec licenses. Qt's LGPL obligations extend beyond simply linking dynamically. These are concrete consequences of shipping a privileged local interface and its dependencies. ([Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security), [pywebview local API security](https://pywebview.flowrl.com/guide/security.html), [Qt LGPL obligations](https://www.qt.io/development/open-source-lgpl-obligations), [Qt licensing](https://doc.qt.io/qt-6/licensing.html))

## Four stages keep implementation measurable

**Stage one: package one complete workflow.** Agree on the analyzer compatibility boundary and release platforms; create a separate desktop adapter; package import, worker analysis, report viewing, and audio preview on Windows and macOS with networking blocked. Select Qt or Tauri from that concrete result before expanding the UI. **Stage two: make library work durable.** Add progressive import, catalog migrations, one active worker, queue persistence, duplicate detection, relinking, cancellation, and restart reconciliation. These proposed stages build directly on current services and atomic artifacts. ([Architecture](../docs/architecture.md), [Analysis service](../src/setvector/application/analyze.py), [Artifact store](../src/setvector/storage/artifacts.py))

**Stage three: integrate inspection.** Separate chart data from export, add the playback adapter, optional waveform/preview caches, deliberate metadata support, and accessible navigation. **Stage four: scale from measurements.** Benchmark the planned 200–2,000-track collections and long recordings, then consider persistent workers, limited concurrency, or streaming decoding. The decoder currently reads complete audio and creates a contiguous copy even though parts of extraction are chunked. Arithmetic illustrates the memory risk: one hour of stereo 44.1 kHz float32 audio is about 1.18 GiB per buffer before copies, resampling, and report generation. This is an allocation estimate, not a measured peak. ([Architecture](../docs/architecture.md), [Audio ingestion](../src/setvector/ingestion/audio.py), [Baseline extraction](../src/setvector/analysis/baseline.py))

Minimum OS versions, Intel Mac support, maximum recording duration, memory limits, desired batch time, distribution channel, and signing resources remain unresolved release requirements. They should be settled before dependent implementation. Native playback precision, installer size, startup time, and cancellation latency also remain unmeasured; DJ-style mixing, time stretching, and controller support are outside the proposed analysis-and-preview product.

## Conclusion

The first durable investment is the boundary between desktop state, worker control, and scientific artifacts. **Inference:** keeping these independent lets SetVector replace a shell, add a CLI workflow, or revise playback without changing what an analysis result means. A small packaged workflow on both operating systems will resolve the most consequential uncertainties earlier than a broad interface prototype.
