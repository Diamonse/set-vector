# Desktop implementation and delivery

## Which desktop implementation best fits SetVector?

### Takeaway

**Conditional recommendation: PySide6 Widgets for the library and job controls, Qt WebEngine for the existing chart, and a separately packaged Python analysis process.** This is an engineering inference about the current Python and HTML codebase, not a measured framework winner. Keep Tauri as the strongest alternative when the intended interface is predominantly custom HTML. Decide from a small packaged workflow on both target operating systems before building the full library interface. [Repository architecture](../../docs/architecture.md), [existing report renderer](../../src/setvector/visualization/html.py), [Qt Python deployment](https://doc.qt.io/qtforpython-6/deployment/deployment-pyside6-deploy.html), [Tauri sidecars](https://v2.tauri.app/develop/sidecar/)

### Cited Findings

- SetVector currently declares a Python package with librosa, NumPy, SciPy, SoundFile and soxr. Its current renderer embeds audio bytes and chart assets into standalone HTML. Thus every desktop route must package a substantial native Python dependency graph; merely choosing a small window wrapper does not remove that work. The first two statements are source observations; the final statement is an inference. [Package configuration](../../pyproject.toml), [HTML renderer](../../src/setvector/visualization/html.py)
- Qt WebEngine deploys its own browser helper executable and resources. Its browser process separation is additional to the analysis-worker separation the application must implement. The framework supports Windows and macOS, but its platform notes explicitly exclude the Mac App Store. [WebEngine deployment](https://doc.qt.io/qt-6/qtwebengine-deploying.html), [platform notes](https://doc.qt.io/qt-6/qtwebengine-platform-notes.html)
- Qt exposes asynchronous process start, output and completion facilities through QProcess. Blocking wait calls on the GUI thread may freeze the interface. On Windows `terminate()` posts WM_CLOSE; a console child without the required event loop can require `kill()`. Therefore cancellation cannot assume that calling `terminate()` stops the packaged analyzer. [QProcess](https://doc.qt.io/qt-6/qprocess.html)
- Tauri documents packaged Python executables as sidecars, requires target-specific binary names, and supports stdin/stdout communication. This lets the same packaged worker serve Qt or Tauri without adding an HTTP server. [Tauri sidecars](https://v2.tauri.app/develop/sidecar/)
- Tauri uses WebView2 on Windows and WKWebView on macOS. macOS WebKit follows operating-system updates. A successful Chromium report test does not establish macOS WebKit behavior; this last statement is an inference from the different engines. [Tauri webview versions](https://v2.tauri.app/reference/webview-versions/)
- Electron has a main process and Chromium renderer processes, plus Node capabilities. Its security guidance assigns runtime maintenance to the application distributor and recommends sandboxing, context isolation, controlled navigation, and validated IPC. Forge distinguishes packaging from installer creation and publishing. [Electron process model](https://www.electronjs.org/docs/latest/tutorial/process-model), [security](https://www.electronjs.org/docs/latest/tutorial/security), [Forge lifecycle](https://www.electronforge.io/core-concepts/build-lifecycle)
- pywebview provides serverless Python/JavaScript integration and local-server alternatives. Its freezing guide recommends py2app on macOS and PyInstaller on Windows; it cautions that unused installed GUI dependencies can accidentally be bundled. [Architecture](https://pywebview.flowrl.com/guide/architecture.html), [freezing](https://pywebview.flowrl.com/guide/freezing.html)
- Toga has an embedded WebView on Windows and macOS; on Windows it requires WebView2. Briefcase documents tested macOS and Windows packaging targets. They are credible Python alternatives, but those documentation claims do not verify SetVector's numerical wheels, worker supervision, media controls, or chart behavior. [Toga WebView](https://toga.beeware.org/en/stable/reference/api/widgets/webview/), [Briefcase platform support](https://briefcase.beeware.org/en/stable/reference/platforms/index.html)

### Inferences

The matrix below is an architecture assessment based on the cited mechanisms above. “Unmeasured” is deliberate; no empty-shell download-size benchmark is being treated as a SetVector result.

| Criterion | PySide6 + WebEngine + worker | Tauri + Python sidecar | Electron + Python sidecar | pywebview + worker | Toga + Briefcase + worker |
|---|---|---|---|---|---|
| Existing code fit | Python host, reusable HTML chart; best fit when native controls dominate | Reusable HTML chart, new Rust host and web application lifecycle | Reusable HTML chart, new JS/Node host | Python host and reusable HTML chart | Python host and WebView; additional widget/bridge evaluation |
| Analysis isolation | Explicit QProcess worker | Explicit sidecar | Explicit child process from privileged host | Must add supervised worker | Must add supervised worker |
| Offline runtime | Bundle Python, Qt, Chromium assets, decoder | Bundle Python; provision Windows webview; macOS webview supplied by OS | Bundle Python, Electron/Chromium/Node | Bundle Python and selected webview dependencies | Bundle Python and platform dependencies |
| Playback/interactive chart | HTML preview initially; Qt Multimedia is a native fallback | Web playback differs across OS engines; native playback requires added integration | Consistent Chromium family; native playback remains added integration | OS webview behavior needs tests | WebView behavior and transport bridge need tests |
| Size/RAM | Unmeasured; bundled Chromium and native stack matter | Unmeasured; full offline Windows runtime matters | Unmeasured; bundled Chromium/Node plus Python matter | Unmeasured; system webview may reduce shell payload | Unmeasured; system webview may reduce shell payload |
| Accessibility | Standard widgets + web chart semantics; test focus crossing | Web semantic controls and focus management | Web semantic controls and focus management | Web semantic controls and focus management | Native widgets + web chart semantics; test focus crossing |
| Delivery machinery | Freezer plus selected installer/signing pipeline | Bundler, sidecar, scoped native APIs, optional signed updater | Forge packaging/makers, optional updater | Application assembles more delivery components | Briefcase packaging; verify required integration |
| Maintenance burden | Python/Qt plus chart JS; browser updates still owned | Rust, web build, Python, two OS webviews | JS/Node, web build, Python, bundled browser | Python/web assets, packaging and OS-webview differences | Python/Toga/Briefcase plus chart bridge |
| Main selection trigger | Current default if native library/job UI fits | Choose if most application screens are web UI, or Qt distribution constraint is unacceptable | Choose only if measured webview incompatibility or team/platform requirements justify it | Candidate for narrow application if packaging acceptance passes | Reconsider if native controls are essential and Qt is rejected |

Use **hard gates before preference scoring**: offline install and use, analysis isolation, correct artifacts, usable playback, accessible core workflow, and viable signing/licensing must all pass. Then compare actual integration hours, bundle footprint, startup, UI response, and maintenance ownership. Do not fabricate 1–5 scores before builds exist. Weight implementation effort most strongly for the current project, while allowing a store requirement or a predominantly web product to override the default. This recommendation follows the existing library-first architecture and the differing platform mechanisms. [Architecture](../../docs/architecture.md), [Qt platform constraints](https://doc.qt.io/qt-6/qtwebengine-platform-notes.html), [Tauri architecture](https://v2.tauri.app/develop/sidecar/)

For Qt, propose native import/library/queue/error controls around one reusable chart surface. Start with the current report's audio transport, then introduce QMediaPlayer only when packaged codec, synchronization or workflow evidence demands it. A player adapter should expose play/pause/seek/current time/duration/errors, with exactly one authoritative playback clock. QMediaPlayer supplies transport/position APIs; WebChannel supplies the JavaScript bridge. Native Qt playback currently defaults to an FFmpeg backend and still requires platform-specific tests. These are implementation recommendations, not existing features. [QMediaPlayer](https://doc.qt.io/qt-6/qmediaplayer.html), [WebChannel](https://doc.qt.io/qt-6/qtwebchannel-javascript.html), [Qt Multimedia](https://doc.qt.io/qt-6/qtmultimedia-index.html)

### Gaps

- No framework candidate was built, timed, profiled, signed, or tested here. No verified winner exists for startup, memory, package size or rendering smoothness.
- A mostly web interface could make Tauri the lower-maintenance route despite Python being the engine language. The UI proportion and developer skill mix remain product/team inputs.
- Neither normal preview playback nor these desktop frameworks establishes DJ mixing, sample-accurate cueing, time stretching, controller support, or audio-device latency requirements.
- Qt's live deployment page retains a Windows Vista statement while the supported-platform table for Qt 6.11 lists Windows 10 1809+/Windows 11 and macOS 13+. Treat the version-specific supported-platform table and actual wheel requirements as the basis of a proposed support floor, then verify it. Do not copy the Vista statement into release promises. [Deployment page](https://doc.qt.io/qt-6/qtwebengine-deploying.html), [supported platforms](https://doc.qt.io/qt-6/supported-platforms.html)

## What proof should precede broader implementation, and why this order?

### Takeaway

**Propose a capped eight engineering-day experiment, with a maximum three-day Tauri comparison only if Qt hits a material blocker or the UI direction favors the web.** First prove the actual packaged worker; next prove the shell, chart and playback; then test interruption and installation. This order resolves failures that can invalidate the implementation before investing in catalog screens. The duration is a planning budget, not an estimate established by a benchmark. [Python package dependencies](../../pyproject.toml), [PyInstaller model](https://pyinstaller.org/en/stable/operating-mode.html), [Qt deployment](https://doc.qt.io/qtforpython-6/deployment/deployment-pyside6-deploy.html)

### Cited Findings

- PyInstaller produces a bundle specific to its build OS/interpreter; end users do not need Python installed. Directory bundles support inspection of collected files. Its one-file mode extracts files during startup. [PyInstaller operation](https://pyinstaller.org/en/stable/operating-mode.html)
- `pyside6-deploy` wraps Nuitka, keeps configuration in a specification, and supports standalone-directory and one-file modes. It is a freezer route, not a complete installer/update design. [pyside6-deploy](https://doc.qt.io/qtforpython-6/deployment/deployment-pyside6-deploy.html)
- PyInstaller defaults to the active Mac architecture. A universal2 application needs compatible binary slices throughout; concatenating two frozen one-file applications with `lipo` does not work. This makes separate architecture builds a lower-complexity initial proposition. [PyInstaller macOS architecture notes](https://pyinstaller.org/en/stable/feature-notes.html)
- QWebEngineView's `setHtml()` uses a data URL limited to roughly 2 MB. Load the current standalone report as a file URL in the experiment; do not feed its embedded audio through `setHtml()`. [QWebEngineView](https://doc.qt.io/qt-6/qwebengineview.html)
- Qt standard widgets supply accessibility support, but custom elements need appropriate semantics. Electron likewise applies web accessibility practices. These are mechanisms, not proof that SetVector's canvas chart or controls are accessible. [Qt accessibility](https://doc.qt.io/qt-6/accessible.html), [Electron accessibility](https://www.electronjs.org/docs/latest/tutorial/accessibility)

### Inferences

Proposed sequence and evidence, all as research recommendations:

| Timebox | Build or investigate | Exit evidence | Why before the following step |
|---|---|---|---|
| Day 1 | Freeze a representative analysis command and real dependency set on Windows x64 and macOS arm64; record exact tool/wheel versions | Analyzer works without Python installed, with networking blocked; output matches same-platform unfrozen run within declared numerical tolerance | Every shell depends on this; finding a numerical-wheel/freezer failure after UI construction wastes that work |
| Days 2–3 | Minimal Qt window, local file picker, asynchronous worker launch, current report as file, preview transport | Import → analyze → inspect → preview succeeds on both OSs; logs include process tree, bundle sizes, first-run and warm timings | Establishes the whole workflow with little interface investment |
| Day 4 | Cancellation, worker crash, UI close and reopen, missing audio, malformed file, Unicode paths | Exactly one terminal job result; no orphan worker; valid published artifacts remain readable; incomplete output is not shown as success | Catalog and queue durability must reflect real process outcomes |
| Day 5 | Compare report-player codec behavior with required audio formats; prototype QMediaPlayer bridge only if needed | Separate analysis/playback format matrix, seek and chart-clock measurements under load | Decoder success and player success differ; discover media-path changes before polishing transport |
| Days 6–7 | Directory bundle → Windows setup package / Mac app in DMG; test clean install, replacement upgrade, blocked networking and accessibility | Installed-artifact acceptance table and upgrade preservation results; signed/notarized candidate if credentials available | A developer checkout is not the delivered product; helper signing and missing runtime problems can appear only here |
| Day 8 | Review evidence and select shell/freezer; record failures, repair cost and footprint | Short decision record with measured results and explicit platform gaps | Makes framework choice evidence-based and stops open-ended tool exploration |

The comparison extension reuses the identical Python worker and identical representative report. Allocate at most three days to a minimal Tauri window and offline package; compare actual hours and acceptance failures, not unrelated demo quality. If Qt succeeds and no web/store requirement favors Tauri, stop the comparison. If the worker fails, fix its distribution boundary before comparing shells. [Tauri sidecar compatibility](https://v2.tauri.app/develop/sidecar/), [Qt process boundary](https://doc.qt.io/qt-6/qprocess.html)

The proposed initial deployment matrix is Windows x64 and native macOS arm64 on a declared minimum OS plus one current OS. Intel Mac is conditional: add a separate x86_64 build only when its user need, supported dependency wheels, CI and real test hardware are established. Rosetta smoke tests alone should not constitute an Intel support claim. Windows ARM is a separate scope decision. The exact minimum OS cannot be derived from Qt alone because all bundled wheels and native libraries must support it. [Qt supported platforms](https://doc.qt.io/qt-6/supported-platforms.html), [PyInstaller architectures](https://pyinstaller.org/en/stable/feature-notes.html)

Proposed acceptance targets below are initial budgets for an analysis-and-preview app. They are intentionally falsifiable, require a recorded reference machine, and are not claims about present SetVector behavior:

| Measurement | Proposed gate / recording method |
|---|---|
| Offline installation and operation | Install, first launch, analyze, cached reopen, chart, preview and export all pass with network blocked and no Python/developer tools; installer contains required runtimes |
| Worker correctness | Exact asset/config identity and expected schema; numerical arrays compared against the same dependency environment using existing domain tolerances; explicitly record tolerances |
| UI responsiveness | During one analysis, p95 interaction acknowledgement under 100 ms and no main-thread stall over 500 ms during a scripted 60-second interaction sequence |
| Startup | Report cold and warm independently; proposed p95 warm interactive window ≤3 s and cold ≤8 s over ten runs on the reference machine; first analysis/JIT measured separately |
| Cancellation/crash | UI acknowledges cancel ≤100 ms; worker exits ≤2 s after hard-cancel deadline; test each pipeline boundary, close/reopen, and repeated cancel 20 times; no live orphan or false success |
| Preview/seek | Analyze/play each selected WAV, AIFF, FLAC and MP3 fixture; 20 seeks each including VBR; proposed settled player position within 100 ms of target; chart/player offset p95 ≤100 ms during preview under analysis load |
| Memory | Record total process-tree peak RSS/working set, not only parent; no growth greater than 100 MiB after 20 repeated select/play/close cycles following warmup; long-track peak must fit a separately declared machine budget |
| Bundle footprint | Record compressed installer, installed footprint, optional preview cache, duplicate runtime payloads; provisional investigation triggers >500 MiB installer or >1.5 GiB install, not automatic scientific limits |
| Accessibility | Complete import, start, cancel, select result, play/pause and seek entirely by keyboard; meaningful focus and labels with NVDA or Narrator and VoiceOver; textual/table alternative for chart values |
| Upgrade | Replace v0 with v1; existing analyses, settings and paths survive; induced migration failure leaves a recoverable backup; no source music modification |
| Real delivery | Validate final downloaded signed Windows artifact and notarized/stapled Mac delivery on a clean machine; distinguish “packaging works” from “public release verified” |

Keep the exact budgets adjustable until representative hardware and listening expectations are agreed. If a budget fails, record which component causes it before changing shells: analysis memory, web renderer memory, duplicate packaged Python, codec initialization, report assembly and JIT startup are different remedies. The process-model and freezer evidence justify measuring the entire process tree. [Electron process model](https://www.electronjs.org/docs/latest/tutorial/process-model), [Qt WebEngine helper](https://doc.qt.io/qt-6/qtwebengine-deploying.html), [PyInstaller operation](https://pyinstaller.org/en/stable/operating-mode.html)

### Gaps

- Actual baseline hardware, maximum recording duration, acceptable batch duration and RAM budget are unresolved; the suggested numbers must not become unexplained promises.
- Signed delivery depends on available signing identities and notarization access. If absent, the experiment can establish unsigned package feasibility but must mark the final delivery gate incomplete.
- No measured cross-platform result has been produced by this research. The test plan is the next implementation work, not completed verification.

## How should licensing, signing, offline installation and updates shape the implementation?

### Takeaway

Choose a complete installer and direct signed distribution for the initial Qt product, put user artifacts outside the installation directory, and begin with replacement installs. Add automatic updating after migration and recovery work is established. This ordering is a recommendation: automatic delivery increases the consequence of a bad migration while adding little to the first proof that local analysis works. [Qt distribution constraints](https://doc.qt.io/qt-6/qtwebengine-platform-notes.html), [Tauri updater](https://v2.tauri.app/plugin/updater/), [Electron updating](https://www.electronjs.org/docs/latest/tutorial/updates)

### Cited Findings

- Tauri's default Windows installer downloads WebView2 if needed. Its documented offline option adds approximately 127 MB; a fixed runtime adds approximately 180 MB. Those are documentation estimates for the runtime, not measured SetVector package sizes. This materially weakens blanket claims that Tauri's complete offline installer must be tiny. [Windows installer](https://v2.tauri.app/distribute/windows-installer/)
- Qt WebEngine requires its helper/resources, and Qt Multimedia's default FFmpeg path requires the relevant binaries. Qt warns that codec behavior can differ across target platforms. Include all used media dependencies in an offline build instead of relying on a development machine's global installation. [WebEngine deployment](https://doc.qt.io/qt-6/qtwebengine-deploying.html), [Qt Multimedia](https://doc.qt.io/qt-6/qtmultimedia-index.html)
- Tauri documents Developer ID Application signing for direct macOS distribution and notarization through Apple credentials. PyInstaller can sign collected Mac binaries, but ad-hoc signatures are not equivalent to a publisher-signed/notarized release. [macOS signing](https://v2.tauri.app/distribute/sign/macos/), [PyInstaller signing notes](https://pyinstaller.org/en/stable/feature-notes.html)
- Windows signing identifies the publisher; Microsoft explicitly says even signed new binaries can trigger SmartScreen and that EV certificates no longer bypass its reputation system. Treat signing verification and reputation prompts as separate observations. [Microsoft SmartScreen](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)
- Tauri's updater requires artifact signatures that cannot be disabled. Its public/private update keys are distinct from OS signing identities. Electron supplies an autoUpdater mechanism and describes hosted update options. Neither makes user-data migration or rollback automatic. [Tauri updater](https://v2.tauri.app/plugin/updater/), [Electron updates](https://www.electronjs.org/docs/latest/tutorial/updates)
- Qt's LGPL guidance describes corresponding library source availability, notices, and the user's ability to replace/relink and run the modified library. Dynamic linking alone is not the complete obligation. Some Qt modules are GPL-only under their open-source option. [Qt LGPL obligations](https://www.qt.io/development/open-source-lgpl-obligations)
- Qt WebEngine's Qt portion has commercial or LGPL/GPL options; the Chromium portion has multiple third-party licenses, including LGPL components. Inspect the exact distributed components even with a commercial Qt license. Electron's main repository uses MIT; that does not replace its bundled dependency notices. [Qt WebEngine licensing](https://doc.qt.io/qt-6/qtwebengine-licensing.html), [Electron license](https://github.com/electron/electron/blob/main/LICENSE)
- The repository already records more than its top-level Apache license: package metadata includes Apache-2.0, MIT and OFL-1.1 for shipped assets. A binary distribution adds another dependency inventory rather than replacing this metadata. [Package metadata](../../pyproject.toml)

### Inferences

- Start with a pinned PyInstaller directory build, with UI and worker as explicit entry points. Investigate whether a shared collected runtime can avoid duplicated numerical/Qt payloads, but preserve separately launchable worker behavior. Only switch to `pyside6-deploy`/Nuitka when a concrete missing hook, signing issue or measured overhead justifies the experiment. Do not promise that compilation accelerates NumPy/librosa algorithms. [PyInstaller operating model](https://pyinstaller.org/en/stable/operating-mode.html), [Qt deployment tool](https://doc.qt.io/qtforpython-6/deployment/deployment-pyside6-deploy.html)
- Use a versioned build manifest listing source revision, Python version, wheel hashes/versions, freezer, UI/browser runtime, codecs and target architecture. Keep release data directories stable. The installer should replace program files while catalog migrations explicitly manage user data. This is a reproducibility/recovery design recommendation, not a feature supplied by freezing. [Repository architecture](../../docs/architecture.md), [Forge package/make distinction](https://www.electronforge.io/core-concepts/build-lifecycle)
- Prepare a dependency bill of materials, included notices, corresponding-source delivery/offer as applicable, and a documented library-replacement route for the LGPL build. Examine the exact FFmpeg configuration and avoid introducing GPL-only modules accidentally. Verify obligations for the chosen bundle before broad distribution; do not claim the Apache project license clears every dependency. [Qt LGPL guidance](https://www.qt.io/development/open-source-lgpl-obligations), [WebEngine license inventory](https://doc.qt.io/qt-6/qtwebengine-licensing.html), [Multimedia licensing](https://doc.qt.io/qt-6/qtmultimedia-index.html)
- Treat downloaded/manual updates and later automatic updates as optional online actions. Core startup must never wait for update discovery. Verify rollback of program files separately from restoration of a migrated catalog; an old executable may not understand a newer database schema. [Repository offline requirements](../../docs/architecture.md), [Tauri update mechanism](https://v2.tauri.app/plugin/updater/)
- Keep reports local, escape metadata, restrict navigation and the bridge to named operations, and avoid exposing general shell/filesystem execution to JavaScript. Child-process isolation controls lifetime and crash propagation; it is not an operating-system sandbox for arbitrary audio parsing. [Electron security principles](https://www.electronjs.org/docs/latest/tutorial/security), [QProcess](https://doc.qt.io/qt-6/qprocess.html)

### Gaps

- This research did not inspect final binary licenses, execute library replacement, sign installers, verify notarization, or validate offline Gatekeeper behavior. These remain artifact-level release checks.
- Apple documentation pages exposed only a JavaScript notice in the research browser, and their linked Markdown retrieval failed; current framework signing guidance was used as the operational source. Apple should be consulted directly during the signing experiment. [Apple notarization documentation](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)
- No commercial-license requirement is asserted. The appropriate open-source or commercial route depends on the complete distribution and its actual ability to satisfy the applicable terms.
