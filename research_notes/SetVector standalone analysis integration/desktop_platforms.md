# Desktop platforms and distribution

## Which desktop approach best fits the first SetVector release?

### Takeaway

**Recommendation (engineering judgment): use PySide6 with a native application shell and an embedded, local Qt WebEngine report view for the first Windows/macOS release.** Preserve the existing Python application services and report assets; run expensive analysis in a separate worker process. This minimizes the change to a Python-first project while delivering an installed application with its own window. Tauri is the preferred alternative if the intended product is predominantly a web interface and the team accepts a Rust/JavaScript/Python build pipeline. This recommendation assumes direct distribution, because Qt WebEngine excludes the Mac App Store. [Qt for Python](https://doc.qt.io/qtforpython-6/), [QWebEngineView](https://doc.qt.io/qt-6/qwebengineview.html), [Tauri sidecars](https://v2.tauri.app/develop/sidecar/), [Qt WebEngine platform notes](https://doc.qt.io/qt-6/qtwebengine-platform-notes.html)

### Cited Findings

| Option | Integration and desktop behavior | Distribution/maintenance consequence | Assessment for SetVector |
|---|---|---|---|
| PySide6 / Qt | Official Python Qt bindings; application services can remain Python. QWebEngineView displays HTML within a widget. | Qt's deployment tool wraps Nuitka and produces Windows executables/macOS apps; Qt WebEngine includes Chromium and requires its resources/helpers. | Best initial integration fit; native controls plus existing report is an incremental route. [Python bindings](https://doc.qt.io/qtforpython-6/), [deployment](https://doc.qt.io/qtforpython-6/deployment/deployment-pyside6-deploy.html), [WebEngine platform notes](https://doc.qt.io/qt-6/qtwebengine-platform-notes.html) |
| Tauri 2 + Python sidecar | HTML/JS interface, Rust host, packaged Python executable. Official docs explicitly describe Python CLIs/API servers bundled using PyInstaller. Sidecars need binaries named for each target architecture. | Windows WebView2 and macOS WKWebView produce an OS-dependent rendering matrix. Bundler, scoped permissions, updater, and CI recipes are supplied. | Good product-oriented web UI route; more integration boundaries than Qt. [sidecars](https://v2.tauri.app/develop/sidecar/), [webviews](https://v2.tauri.app/reference/webview-versions/), [Tauri repository](https://github.com/tauri-apps/tauri) |
| Electron + Python sidecar | HTML/JS interface with bundled Chromium/Node; the main process can spawn a packaged Python executable with Node child-process APIs. | Electron Forge packages the app and makes installers. The application distributor must update the bundled browser/runtime and package Python separately. | Useful if identical Chromium behavior and existing JS expertise outweigh additional runtime footprint; no inherent Python packaging advantage. [Electron security](https://www.electronjs.org/docs/latest/tutorial/security), [Node child processes](https://nodejs.org/api/child_process.html), [Forge lifecycle](https://www.electronforge.io/core-concepts/build-lifecycle) |
| pywebview or external browser + loopback service | pywebview offers a Python/JS bridge and embedded webview, or a local web-server architecture. An external-browser version opens the local app in the user's browser rather than supplying its own desktop shell. | pywebview documents py2app for macOS and PyInstaller for Windows/Linux; WebView2 must be provisioned on Windows. A local REST service adds CSRF/session/lifecycle work. | Small bridge prototype or internal preview; less complete distribution machinery than Tauri. An external browser should not be presented as the native standalone UX the user requested. [architecture](https://pywebview.flowrl.com/guide/architecture.html), [freezing](https://pywebview.flowrl.com/guide/freezing.html), [engines](https://pywebview.flowrl.com/guide/web_engine), [security](https://pywebview.flowrl.com/guide/security.html) |

- “Standalone installed application” and “native widgets” are different requirements: Tauri uses a native window with an OS webview; Qt can use Qt widgets plus an embedded browser. Neither requires a hosted service. The need for an OS webview should not be confused with needing a browser window or cloud server. [Tauri architecture/readme](https://github.com/tauri-apps/tauri), [Qt bindings](https://doc.qt.io/qtforpython-6/), [pywebview architecture](https://pywebview.flowrl.com/guide/architecture.html)
- Qt WebEngine's `setHtml()` cannot display content exceeding its approximately 2 MB URL limit. Load a generated local report using a URL, or use an explicitly scoped application resource protocol, rather than passing a report with embedded audio to `setHtml()`. The loading API is documented separately from the convenience function. [QWebEngineView](https://doc.qt.io/qt-6/qwebengineview.html)
- Tauri supports bidirectional stdin/stdout communication with a child process and permission-scoped sidecar execution. It does not require an HTTP API for the Python integration. [Tauri sidecars](https://v2.tauri.app/develop/sidecar/)

### Inferences

- Proposed Qt structure: native menus, file selection, library/job controls, progress, settings, and error presentation; reuse the report's web chart within the window. Keep UI code as an adapter over application services. A separate worker process provides a controllable boundary for long analyses and cancellation; this is a design recommendation, not a performance benchmark. [Qt bindings](https://doc.qt.io/qtforpython-6/), [QWebEngineView](https://doc.qt.io/qt-6/qwebengineview.html)
- For a later Tauri/Electron migration, keep a narrow versioned worker protocol with job IDs, progress, cancellation, structured errors, and artifact references. Avoid streaming full spectral arrays through JSON. The same worker boundary can serve either shell. This recommendation follows from the documented child-process mechanisms. [Tauri sidecars](https://v2.tauri.app/develop/sidecar/), [Node child processes](https://nodejs.org/api/child_process.html)
- For a Qt MVP, retain the embedded report's existing transport first if its playback passes the packaged tests. If browser decoding is insufficient, use Qt Multimedia for playback and send its time position to the chart through an explicit bridge. Avoid maintaining two competing playback clocks. [Qt Multimedia](https://doc.qt.io/qt-6/qtmultimedia-index.html), [Qt WebEngine media features](https://doc.qt.io/qt-6/qtwebengine-features.html)

### Gaps

- No candidate was built or benchmarked in this research. Claims about smallest installer, fastest startup, lowest RAM, or lowest effort would need representative builds containing SetVector's actual numerical dependencies.
- The user's meaning of native, visual direction, expected library size, playback precision, and future store distribution remain product decisions. A requirement for an almost entirely custom web interface could change the recommendation to Tauri immediately.
- The minimum supported Windows/macOS versions and whether Intel Macs are in the first release need a deliberate support policy based on all numerical wheels and UI components, not the shell's advertised minimum alone.

## How should the app be packaged, signed, updated, and tested?

### Takeaway

**Recommendation:** ship complete signed installers with Python and numerical dependencies included, using per-OS CI. Start with manual replacement installs and preserve user artifacts outside the installation directory; add optional signed in-app updates only after the packaged application is reliable. PyInstaller explicitly supports shipping applications to users without an installed Python and requires platform-specific builds. [PyInstaller operation](https://pyinstaller.org/en/stable/operating-mode.html)

### Cited Findings

- `pyside6-deploy` wraps Nuitka, supports `onefile` and `standalone` modes, and creates a reproducible `pysidedeploy.spec`. It produces an executable/app bundle; this is distinct from an installer/update system. Qt also documents other Python freezing tools. [pyside6-deploy](https://doc.qt.io/qtforpython-6/deployment/deployment-pyside6-deploy.html), [Qt deployment overview](https://doc.qt.io/qtforpython-6.8/deployment/index.html)
- Qt Installer Framework supplies cross-platform installers and maintenance/update tools. It is a separate product/tooling choice, not automatic functionality of a frozen PySide app. [Installer Framework overview](https://doc.qt.io/qtinstallerframework/ifw-overview.html)
- PyInstaller builds are specific to the build OS and interpreter. On macOS its default is the active single architecture. Universal2 requires compatible slices across dependencies; joining two frozen one-file executables using `lipo` does not create a valid universal app. [PyInstaller operation](https://pyinstaller.org/en/stable/operating-mode.html), [macOS architecture and signing notes](https://pyinstaller.org/en/stable/feature-notes.html)
- Tauri produces Windows MSI through WiX or setup EXE through NSIS; MSI creation requires Windows. An offline WebView2 installer can be bundled. The docs currently estimate approximately 127 MB extra for that option and approximately 180 MB for a fixed runtime; these are documentation estimates, not SetVector measurements. [Windows installer](https://v2.tauri.app/distribute/windows-installer/)
- Tauri's GitHub Actions guidance covers macOS and Windows builds. Python sidecar creation still has to be added before bundling. [Tauri CI](https://v2.tauri.app/distribute/pipelines/github/), [sidecars](https://v2.tauri.app/develop/sidecar/)
- Electron Forge distinguishes package, make, and publish. Packaging creates OS application bundles and handles macOS signing/notarization; makers create distributable installers. [Forge lifecycle](https://www.electronforge.io/core-concepts/build-lifecycle)
- Direct macOS distribution should use Developer ID Application signing and notarization. Tauri documents signing identities, CI credentials, notarization, and stapling. Electron Forge supplies corresponding `osxSign`/`osxNotarize` integration. [Tauri macOS signing](https://v2.tauri.app/distribute/sign/macos/), [Forge macOS signing](https://www.electronforge.io/guides/code-signing/code-signing-macos)
- Code signing on Windows establishes publisher identity but does **not** guarantee the absence of SmartScreen warnings. Microsoft says new signed binaries may still warn and EV certificates no longer get automatic positive reputation. Prefer this Microsoft statement over a framework guide's shorthand implying signing removes warnings. [Microsoft SmartScreen](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation), [Tauri Windows signing](https://v2.tauri.app/distribute/sign/windows/)
- Tauri update signatures are mandatory and use a dedicated public/private key pair; its update mechanism is separate from OS code signing. Electron offers `autoUpdater` and documents update-server behavior. Update availability is an optional online feature and need not determine whether analysis starts. [Tauri updater](https://v2.tauri.app/plugin/updater/), [Electron updates](https://www.electronjs.org/docs/latest/tutorial/updates)
- Qt explicitly states apps using Qt WebEngine are incompatible with the Mac App Store because of private APIs and App Sandbox interaction. This is a material limitation of the recommended hybrid Qt shell, not a restriction on direct signed/notarized distribution. [Qt WebEngine platform notes](https://doc.qt.io/qt-6/qtwebengine-platform-notes.html)

### Inferences

- First packaging spike: use a pinned PyInstaller directory bundle for the Qt app and worker, because dependency inspection/debugging is useful before single-file optimization; evaluate `pyside6-deploy` if it packages the numerical stack more reliably. Choose based on clean-machine execution rather than a generic freezer ranking. [PyInstaller operation](https://pyinstaller.org/en/stable/operating-mode.html), [pyside6-deploy](https://doc.qt.io/qtforpython-6/deployment/deployment-pyside6-deploy.html)
- CI candidates: Windows x64, macOS arm64, and a separate macOS x64 build if Intel support is selected. Bundle all native dependencies, including audio decoding and numerical libraries. Sign nested executable content before the enclosing app/installer and verify the final downloadable artifacts. Architecture completeness is especially consequential for Python extension modules. [PyInstaller macOS notes](https://pyinstaller.org/en/stable/feature-notes.html), [Tauri macOS signing](https://v2.tauri.app/distribute/sign/macos/)
- Release acceptance should install on machines with no Python/Node/Rust, then block networking and exercise import, analysis, cached reopening, chart loading, playback, export, interruption, and restart. Test paths containing spaces and Unicode, moved/deleted source files, and artifacts surviving an update. This is a proposed validation plan motivated by packaged dependency and per-platform behavior, not a completed test claim. [PyInstaller operation](https://pyinstaller.org/en/stable/operating-mode.html), [Qt Multimedia platform differences](https://doc.qt.io/qt-6/qtmultimedia-index.html)
- Prefer a complete installer download to a network bootstrapper for the initial app. Tauri's normally smaller wrapper does not imply a small total product when Python, NumPy/SciPy/other binaries, and an offline WebView2 runtime are included. [Tauri Windows installer](https://v2.tauri.app/distribute/windows-installer/), [PyInstaller operation](https://pyinstaller.org/en/stable/operating-mode.html)

### Gaps

- Signing identities/accounts, budgets, CI credentials, direct-download hosting, minimum OS versions, and ARM64 Windows scope have not been selected.
- Dependency-specific freezer hooks, JIT/cache behavior, bundle size, antivirus false positives, cold-start time, and actual notarization acceptance require a packaging spike with the current locked SetVector environment.
- A complete rollback/update design is not established here. Manual installer replacement is the recommended first-stage scope, not a guarantee that an installer already preserves all user data.

## What playback, accessibility, security, and licensing constraints matter?

### Takeaway

All four approaches can support local playback and interactive charts, but a shipped audio application needs tests against its actual codecs, webview/runtime, and assistive technologies. Keep local music and imported metadata outside privileged web execution, and treat licensing as a property of the complete distributed dependency set. [Qt Multimedia](https://doc.qt.io/qt-6/qtmultimedia-index.html), [Electron security](https://www.electronjs.org/docs/latest/tutorial/security), [Qt licensing](https://doc.qt.io/qt-6/licensing.html)

### Cited Findings

- Qt Multimedia provides `QMediaPlayer`, output-device APIs, and raw-audio output through `QAudioSink`. Its principal backend is FFmpeg; Qt warns that codec/format support can still differ by platform and recommends testing each target. FFmpeg deployment and its applicable notices must be accounted for. [Qt Multimedia](https://doc.qt.io/qt-6/qtmultimedia-index.html)
- Qt WebEngine's codec configuration differs from Qt Multimedia. Support for proprietary audio/video formats depends on build configuration and applicable codec licensing. A successful Python decode does not prove playback in the embedded browser will work. [Qt WebEngine features](https://doc.qt.io/qt-6/qtwebengine-features.html)
- Web Audio describes an audio-processing graph for web applications; it provides a route for web shells, but the specification is not a guarantee of identical codec support or every feature in each OS webview. The accessed 1.1 document is explicitly a Working Draft. [W3C Web Audio](https://www.w3.org/TR/webaudio/), [Tauri webview versions](https://v2.tauri.app/reference/webview-versions/)
- Qt's standard controls provide accessibility metadata via platform APIs, keyboard navigation, and scaling/system palette behavior. Custom controls need additional semantic metadata. Electron activates accessibility features when assistive technology is present and applies web accessibility principles. [Qt accessibility](https://doc.qt.io/qt-6/accessible.html), [Electron accessibility](https://www.electronjs.org/docs/latest/tutorial/accessibility)
- Tauri APIs are available to bundled code by default and can be restricted through capabilities. Permissions reduce exposure after a frontend compromise; they do not make unrestricted native backend logic safe. [Tauri capabilities](https://v2.tauri.app/security/capabilities/)
- Electron recommends sandboxing, context isolation, restrictive CSP, disabling unneeded navigation, validating IPC senders, and avoiding privileged access from untrusted content. Its security guidance also makes maintaining Electron/Chromium/Node versions the app distributor's responsibility. [Electron security](https://www.electronjs.org/docs/latest/tutorial/security)
- pywebview warns about CSRF for local REST APIs and supplies a session-unique token for application verification. Loopback transport is therefore not an authentication boundary by itself. [pywebview security](https://pywebview.flowrl.com/guide/security.html)
- PySide6 is offered under LGPLv3/GPLv3 and commercial licenses. Qt's LGPL guidance requires satisfying source/notices and library replacement/relinking obligations; some modules are GPL-only for open-source users. Dynamic linking alone is not the entire compliance task. [Qt for Python](https://doc.qt.io/qtforpython-6/), [Qt LGPL obligations](https://www.qt.io/development/open-source-lgpl-obligations), [module licensing](https://doc.qt.io/qt-6/licensing.html)
- Tauri code is MIT or MIT/Apache-2.0 where applicable, Electron uses the MIT license, and pywebview uses BSD-3-Clause. These top-level licenses do not replace dependency notices or codec terms. [Tauri license statement](https://github.com/tauri-apps/tauri), [Electron license](https://raw.githubusercontent.com/electron/electron/main/LICENSE), [pywebview license](https://github.com/r0x0r/pywebview/blob/master/LICENSE)

### Inferences

- Prefer a narrow process bridge over an HTTP analysis server for the packaged app. If a loopback service is chosen, bind explicitly to loopback, authenticate the session, validate allowed origins/hosts and file access, reject unintended state-changing requests, and terminate the server with the app. These are design consequences of exposing local APIs, not features a web wrapper automatically guarantees. [pywebview security](https://pywebview.flowrl.com/guide/security.html), [Tauri sidecar IPC](https://v2.tauri.app/develop/sidecar/)
- Load only packaged UI assets and app-generated report data. Escape imported filenames/tags, restrict navigation and resource access, and expose narrowly named operations rather than arbitrary filesystem/shell functions. The desktop app's native bridge makes a report injection materially more consequential. [Electron security](https://www.electronjs.org/docs/latest/tutorial/security), [Tauri capabilities](https://v2.tauri.app/security/capabilities/)
- Playback acceptance should include each promised format, seeking/scrubbing near boundaries, variable bitrate material, long tracks, output-device changes, and chart synchronization under CPU load. Neither a framework overview nor a browser specification establishes SetVector's timing precision. [Qt Multimedia](https://doc.qt.io/qt-6/qtmultimedia-index.html), [Web Audio](https://www.w3.org/TR/webaudio/)
- Test the packaged keyboard workflow with Windows screen readers and macOS VoiceOver. A canvas waveform needs a textual/time-based alternative and accessible transport controls; framework accessibility support does not automatically make a custom chart operable. [Qt accessibility](https://doc.qt.io/qt-6/accessible.html), [Electron accessibility](https://www.electronjs.org/docs/latest/tutorial/accessibility)
- Stage alternatives by evidence: keep Qt if native controls and Python integration work well; select Tauri if the web interface becomes the whole product; select Electron if consistent bundled Chromium behavior proves necessary; use pywebview for a bounded prototype if the extra installer/security lifecycle is acceptable. Do not rewrite the numerical engine for any shell. [Qt bindings](https://doc.qt.io/qtforpython-6/), [Tauri sidecars](https://v2.tauri.app/develop/sidecar/), [Electron runtime/security](https://www.electronjs.org/docs/latest/tutorial/security), [pywebview architecture](https://pywebview.flowrl.com/guide/architecture.html)

### Gaps

- No compatibility statement is made for DJ-grade low-latency mixing, time-stretching, key lock, controller integration, or multichannel cueing. These are separate engine requirements from analysis and audition playback.
- Qt/Tauri/Electron/pywebview do not determine whether every shipped numerical library, decoder, model, or audio codec may be redistributed under SetVector's eventual license. The exact dependency bundle needs an inventory before distribution.
- Accessibility of SetVector's existing report and playback behavior inside each packaged shell have not been tested.
